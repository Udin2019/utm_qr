## Заблокировано средой, не считается успешным

- Docker daemon: `docker info` → `connect: operation not permitted`. Контейнеры не создавались; WordPress и MariaDB не запускались.
- Shell-сеть: `curl -I https://getcomposer.org/composer-stable.phar` → `Could not resolve host`. Composer отсутствует; зависимости не установлены. **composer.lock не создан**, Composer audit и platform checks не выполнены. Сборка явно требует lock, а не разрешает нефиксированные зависимости незаметно.
- PHP CLI не имеет `intl` и `gd`. IDN-тест пропущен; QR/PNG на текущем CLI не исполнялись. rsvg-convert и Inkscape отсутствуют.
- Полный `nginx -t`: сначала ограничения владельцев/системных временных каталогов, затем после переноса временных путей в проект — `socket() ... Operation not permitted`. Синтаксис принят; работа TLS/Basic Auth не подтверждена.
- Браузерного инструмента в сессии нет. Визуальная проверка WordPress не проведена.

## Что ещё требуется до приёмки

1. На хосте с разрешёнными Docker и сетью создать lock, собрать и поднять стенд, проверить сервис setup и версии образов. Затем запустить подготовленные тесты и записать фактические результаты.
2. Проверить браузером все формы, предпросмотр, повторный POST, ошибки ввода, дублирование, назначения, справочники, фильтры и серверную пагинацию. Через WordPress-сессию просмотрщика убедиться в отказе каждой операции изменения и успехе разрешённых выгрузок. Проверить nonce и доступ к скачиваниям.
3. Проверить параллельные GET с подсчётом допущенных лимитером запросов; отказ записи агрегата без потери перехода; недоступную БД с 503. Проверить исходный QR после новой версии профиля.
4. Пройти полную цепочку до реального лендинга и счётчика; подтвердить UTM и конверсию. Проверить реальные HTTPS, DNS/SNI, отсутствие обхода Basic Auth через origin и запрет внутреннего WP на go.
5. Открыть CSV в Excel и BI, импортировать SVG в дизайнерскую программу. Выполнить печатные iOS/Android-пилоты с критериями исходного задания.
6. Сделать и восстановить backup на отдельном стенде, убедиться в сохранности прежнего короткого кода. Зафиксировать релиз и точные версии образов.

## Уточнение по запуску с SSH-терминала пользователя

Пользователь установил Composer-зависимости и собрал контейнеры. По переданному выводу MariaDB healthy, WordPress FPM running. Первичная установка создала 12 таблиц WordPress и одного пользователя, но `home` и `siteurl` остались пустыми; `db_version=61833`. Загрузка WordPress из setup остановилась на странице ошибки БД. Это уточняет первоначальный статус: контейнеры доступны пользователю через SSH, но агент по-прежнему не может обращаться к Docker socket.

Исправлена передача WORDPRESS_CONFIG_EXTRA: wordpress и setup используют один YAML anchor с каноническими HTTPS-адресами. Добавлен shutdown guard: ранний exit(0) WordPress без достижения конца setup теперь возвращает 1; обе ветки проверены отдельными PHP-процессами. Подготовлен `scripts/repair-site-urls.php`: только staging, транзакционное заполнение двух пустых URL, проверка наличия версии схемы и пользователя, отказ от перезаписи заполненных значений, повторный запуск без изменений при совпадении адресов. Проверены PHP-синтаксис, Compose config и 60 доменных утверждений. Восстановление в контейнере и повторная установка на момент записи ещё не выполнены.

## HTTP-приёмка: диагностика счётчика

В тесте подтверждены внутренние 401, публичные 404, корректный HEAD 302/Location/no-store и отсутствие инкремента HEAD. GET вернул 302, но агрегат остался 0. По журналу после расширения диагностики: `counter_failed sqlstate=42000 driver=1143 operation=UPDATE column=placement_id`. SELECT-правка не устранила ошибку. Подготовлена правка UPDATE-привилегий трёх явно указанных колонок только таблицы агрегатов; upsert меняет только get_count. Добавлена проверка второго GET для существующей дневной строки. Применение последней правки и полный HTTP PASS ещё не подтверждены.

## HTTP-приёмка успешно завершена

После выдачи UPDATE на ключевые колонки агрегата пользователь повторно запустил setup и tests/http.py. Получен итог: `PASS: anonymous internal auth, public isolation, redirects, methods, GET/HEAD counters`.

Подтверждены все сценарии текущего HTTP smoke-теста: внутренние анонимные 401, изоляция go/неизвестный код 404, активный и архивный HEAD 302 с ожидаемым назначением/no-store и игнорированием query, HEAD без счётчика, GET и повторный GET с инкрементами, POST 405 без инкремента, отозванный GET 410 без инкремента.
