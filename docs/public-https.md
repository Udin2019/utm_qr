# Домен utmqr.kit-rb.com и доверенный HTTPS

Пользователь подтвердил: A-запись ведёт на его сервер38.180.121.98; Xray на443 больше не используется и его разрешено остановить/отключить. Удаление Xray не разрешалось и не выполняется. Отдельный nginx/certbot уже установлен, certbot.timer существует. Скрипт не устанавливает пакеты и не перезагружает сервер.

## Запуск из обычного SSH-терминала

```bash
cd /root/cargo_utm_qr
python3 scripts/install-public-https.py
```

У агента нет доступа к Docker socket, network/service management или записи /etc, поэтому он готовит файлы; скрипт применяет их только при выполнении пользователем от root в PuTTY.

Скрипт проверяет DNS A, владельцев80/443, ответ origin с перенаправлением на вход WordPress (при первоначальном обновлении допустим прежний401) и наличие программ. При неизвестном владельце порта останавливается. Сохраняет .env, имеющиеся целевые конфиги и приватную копию Xray-конфига и БД в `.runtime/public-https-<UTC>/` (права700/600). Не присылайте эти резервные файлы в чат.

Далее собирает wordpress/setup, добавляет только `/etc/nginx/sites-available/cargo-utmqr.conf` и соответствующую ссылку. Прочие сайты не переписываются. Сначала запускается HTTP-only ACME webroot `/var/www/cargo-utmqr-acme`; Xray ещё может слушать443 на этом этапе. Certbot certonly --webroot запрашивает сертификат для одного домена или использует существующий до срока обновления. При необходимости Certbot попросит email/согласие с условиями в терминале; не вводите выдуманный email и не передавайте учётные данные в чат. Для HTTP-01 порт80 должен быть доступен из Интернета, включая внешний firewall провайдера; DNS AAAA, если есть, тоже должен вести на правильный сервер.

После проверки сертификата скрипт настраивает публичный URL WordPress через `CARGO_PUBLIC_UTM_URL=https://utmqr.kit-rb.com`, сохраняя `CARGO_UTM_HOST=utm.cargo.test` как внутреннее имя и прежний go. Для localhost-origin создаётся отдельный self-signed сертификат на10лет в `secrets/origin-tls`, который доверяется только системному proxy через `/etc/nginx/cargo-origin-ca.crt`; наружу выдаётся Let's Encrypt. Origin остаётся loopback-only и проверяется с CA, без proxy_ssl_verify off. CARGO_TLS_CERT/KEY переключаются на новые внутренние файлы; прежние тестовые файлы не удаляются. Через10лет origin-сертификат нужно перевыпустить и обновить доверие proxy; регулярный публичный сертификат обновляет Certbot.

Создаётся HTTPS-vhost443, выполняется nginx -t, затем **systemctl disable --now xray.service**, reload nginx и локальный HTTPS-запрос с правильным SNI и проверкой публичного сертификата. Ожидается302/303 на вход WordPress. Basic Auth отключён по запросу пользователя. Только явное прохождение этой проверки считается завершённым переключением. Записи БД, пользователи, размещения, UTM и файлы QR не переписываются. При изменении публичного имени может потребоваться заново войти в WordPress: cookie другого домена не переносится браузером.

В конце включаются автозапуск Nginx и certbot.timer. Deploy hook `/etc/letsencrypt/renewal-hooks/deploy/cargo-utmqr-nginx` перезагружает Nginx только при продлении сертификата этого домена. Другие сертификаты/проекты он не меняет.

## Проверки после завершения

```bash
curl -sS -o /dev/null -w 'HTTPS: %{http_code}\n' https://utmqr.kit-rb.com/wp-admin/
curl -sS -o /dev/null -w 'HTTP: %{http_code}\n' http://utmqr.kit-rb.com/
systemctl is-active xray
systemctl is-enabled xray
systemctl is-active nginx
systemctl is-active certbot.timer
certbot renew --cert-name utmqr.kit-rb.com --dry-run
```

Ожидаются HTTPS302/303 без -k, HTTP308, Xray inactive/disabled, nginx и timer active, dry-run успешен. Затем https://utmqr.kit-rb.com/wp-admin/admin.php?page=cargo-utm — индивидуальный WordPress admin из .env; дополнительного Basic Auth нет. Проверить QR-картинку и скачивания с новым URL. Старый тестовый go-домен не стал публичным рабочим доменом автоматически; его следует согласовать отдельно до печати.

## Отказ и восстановление

До успешного публичного HTTPS302/303 скрипт пытается восстановить прежний .env, origin-контейнеры и конфиг целевого сайта. Если нового сайта прежде не было, оставляет HTTP-only ACME-vhost для повторной попытки. Если Xray был активен/включён до переключения и уже был отключён скриптом, при неудаче восстанавливает его предыдущие состояние/автозапуск после удаления конфликта443. Сама конфигурация/клиенты/ключи Xray не меняются. Неисправность после успешного переключения (например таймер) не откатывает уже работающий HTTPS, а сообщается отдельно.

Автоматический откат — best effort, не гарантия при отказе Docker/systemd/диска. В таком случае использовать сохранённые копии и сначала проверить фактических слушателей80/443 и nginx -t. Не удалять тома/сертификаты и не публиковать БД/FPM. SQL backup не восстанавливается автоматически: сайт не должен терять записи, созданные во время установки.

## Фактическая проверка в сессии агента

Пройдены пять изолированных тестов установщика/конфигов, Python compile, PHP/JS и общие локальные проверки, Compose config. На реальных службах скрипт ещё не выполнялся: отключение Xray, выпуск/продление сертификата и публичный HTTPS должны быть подтверждены выводом пользователя. nginx -t для реального vhost выполняется самим установщиком на сервере, после появления сертификатов.

Документация: [Certbot webroot](https://eff-certbot.readthedocs.io/en/stable/using.html#webroot), [Nginx proxy TLS/SNI](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_ssl_server_name).
