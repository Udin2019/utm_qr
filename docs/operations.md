# Эксплуатация и выпуск

## Границы развёртывания

Compose — отдельный проект `cargo-utm`, без публикации портов MariaDB и FPM. По умолчанию Nginx доступен только на loopback. Для staging и production используйте разные каталоги, `.env`, Compose project name (`docker compose -p cargo-utm-staging ...`), тома БД, домены, TLS и наборы пользователей. Не используйте тестовую БД для production.

Публичный FPM имеет только `/opt/cargo/go` и `/tmp` в open_basedir и отдельную учётную запись БД. `scripts/setup.php` выдаёт колонковые права SELECT на размещения и права на атомарный агрегат. WordPress и файлы пользователей не монтируются в go. Для внешнего Nginx перенесите два HTTPS server block из `infra/nginx/default.conf.template`, замените upstream и пути сертификатов по окружению. Проверьте `nginx -t` перед применением. Настройка внешнего reverse proxy, firewall, DNS и TLS не выполняется автоматически.

При наличии внешнего reverse proxy закройте прямой доступ к origin. По явному запросу пользователя Basic Auth отключён; доступ к админке и данным проверяет WordPress. Не создавайте обходных маршрутов к PHP-FPM. Отключите кеширование `/r/` в CDN. Сервер go принимает точный настроенный хост; query не влияет на назначение. Технические access logs сохраняют только время, статус, размер ответа и длительность; IP, UA, query и Authorization туда не попадают. Error logs Nginx для этих хостов отключены из-за возможного попадания request data; приложение пишет фиксированные диагностические коды.

## Подготовка релиза

1. На staging зафиксируйте `composer.lock` настоящим Composer. Выполните `composer install --no-dev --prefer-dist`, `composer check-platform-reqs --no-dev`, `composer audit`.
2. Зафиксируйте проверенные теги/дайджесты образов в `.env`, запишите `docker compose images` в внутренний отчёт без секретов. WordPress должен оставаться поддерживаемым. Не выпускайте релиз на неподтверждённой версии образа.
3. Пройдите локальные и интеграционные проверки, HTTP и визуальную приёмку. Проверьте запрещённые запросы просмотрщика, nonce, скачивания, все офлайн-формы. Отдельно проведите параллельные GET в пределах лимитера; сравните число 302 и прирост счётчика. На staging проверьте отказ записи агрегата (редирект сохраняется) и отказ чтения БД (503).
4. Подготовьте резервную копию, проверьте состав и восстановите её в отдельном стенде. Не останавливайте текущую БД ради копирования файлов тома.
5. Соберите образ. При установке нового кода запустите `docker compose up -d --build`, проверьте `setup` и `wp cargo-utm migrate`, затем `nginx -t` и HTTP-проверки. Не выполняйте `down -v`.
6. Перед печатью проверьте рабочий go-хост в декодированном QR. Утвердите действующие профили и HEX-цвета; условные знаки в production запрещены.

## Резервная копия

Копия БД содержит учётные записи WordPress, SVG и все версии брендов, метки, аудит и суточную статистику. Берегите её как конфиденциальные данные. Вручную выгружайте только в приватный каталог; пароль берётся из среды контейнера и не включается аргументом командной строки:

```bash
umask 077
mkdir -p backups
docker compose exec -T db sh -c 'export MYSQL_PWD="$MARIADB_ROOT_PASSWORD"; exec mariadb-dump --user=root --single-transaction --routines --triggers "$MARIADB_DATABASE"' > backups/cargo-db.sql
```

Команда перезаписывает `backups/cargo-db.sql`: перед повторным запуском выбирайте уникальное имя. Проверьте exit code, ненулевой размер и завершённость дампа без вывода содержимого в чат. Сохраните исходники/образ релиза и lock. Отдельно защищённо сохраните `.env`, сертификаты и htpasswd; храните резервные секреты зашифрованно вне репозитория. При использовании стандартных загрузок WordPress сохраните также wp-content/uploads; векторные профили этого плагина находятся в БД.

## Восстановление

В отдельном **тестовом** окружении поднимите чистую MariaDB и восстановите дамп через stdin:

```bash
docker compose exec -T db sh -c 'export MYSQL_PWD="$MARIADB_ROOT_PASSWORD"; exec mariadb --user=root "$MARIADB_DATABASE"' < backups/cargo-db.sql
```

Восстановление заменяет данные целевой БД: сначала проверьте Compose project name, точную БД и назначение окружения. Поднимите тот же релиз, запустите миграции, восстановите разрешения go-пользователя через сервис setup и проверьте исходный короткий код. Для проверки backup из production используйте изолированную сеть и маршрутизацию, не меняйте живой go-домен.

## Откат

Сохраните предыдущий образ и ревизию исходников. При проблеме откатите код на совместимую со схемой версию, сохранив текущую БД и выданные коды. Текущая миграция только создаёт схему; автоматического удаления данных или отката схемы нет. Если будущая миграция несовместима, сначала подготовьте отдельный план обратной миграции. Не восстанавливайте старый дамп поверх текущей БД без учёта новых выпущенных кодов и GET после backup.

## Рабочие параметры и внешняя приёмка

Оператор согласует `utm`/`go` домены, точные лендинги, TLS и продление. Владелец бренда утверждает контуры и цвета, администратор публикует версии. Пользователи получают индивидуальные WordPress-записи. Владелец аналитики устанавливает Метрику/GA4 на тестовом лендинге, проверяет отсутствие потери query на редиректах и тестовую конверсию. GET — отдельная метрика переходов, не уникальные визиты.

CSV: UTF-8 BOM, `;`, кавычки по правилам CSV, потенциальные формулы предваряются апострофом. Две выгрузки соединяются по `placement_id`; даты суточных агрегатов в UTC. Открытие в реальном Excel и загрузку в BI проверяют на целевых версиях программ.

Дизайнер проверяет импорт SVG, белое поле и подпись короткого адреса. Печатный пилот фиксирует материал, масштаб, расстояние, угол, свет и время на считывание. На каждом iOS/Android устройстве нужно минимум 9 успешных попыток из 10. Движущийся транспорт проверяют в контролируемых безопасных условиях с позиции пешехода. Эти испытания не заменяются декодированием файлов.
