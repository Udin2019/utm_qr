# Каргономика · UTM и QR

Внутренний WordPress-плагин `cargo-utm` и отдельный PHP-редирект для печатных QR. Основание — [исходное задание](CARGONOMICA_UTM_QR_CODEX.md).

**Статус:** установленный стенд прошёл прежние интеграционные, 12 QR- и HTTP-проверки по выводу пользователя. Подготовлено обновление интерфейса 0.2 из `cargonomica-utm-qr-ui.zip`: WordPress-экран, печатные издания, новые пресеты и Roistat. Новое обновление пока не применено к контейнерам и требует повторной приёмки. Composer lock и зависимости уже созданы. Агенту недоступен Docker socket; команды на стенде выполняет пользователь через SSH. Текущее состояние: [MEMORY.md](MEMORY.md).

## Обновление интерфейса из архива

Пользователь согласовал перенос дизайна и всех доработок. Новый экран остаётся в **wp-admin → UTM и QR**, использует БД и серверные обработчики с capabilities/nonce. Демонстрационные localStorage, счётчики и браузерная генерация QR не используются. Рабочая короткая ссылка и файлы доступны после сохранения; до него показываются предварительные метки. Предпросмотр использует серверный URL builder, пример офлайн-кода отмечен явно.

Новое: шестой офлайн-носитель «Печатные издания»; онлайн-пресеты `yandex / cpc`, `vk.ads / cpc`, `avito.ads / cpc`, `tg.ads / cpc`, `newsletter / email` и ручной ввод; опциональные `roistat`/`rs` с макросами из предоставленного прототипа. Публикуются новые версии пресетов; Roistat и версия пресета сохраняются в `tracking_json`, карточке и CSV и сохраняются при смене назначения. Действие макросов в реальных рекламных аккаунтах ещё требует внешней проверки.

Миграция 2 добавляет nullable `tracking_json`, новые шаблоны и тестовые версии профилей с векторным знаком из архива. Существующие размещения, UTM, SVG, short_code и прежние версии не переписываются. Тестовый знак не получает production-утверждение автоматически. Административные страницы аналитики и справочников доступны из бокового меню; для них сохраняется существующий функциональный интерфейс.

На текущем установленном стенде запустите **в SSH-терминале**:

```bash
cd /root/cargo_utm_qr
./scripts/upgrade-ui.sh
```

Скрипт создаёт приватную копию БД и снимки размещений в `.runtime/ui-upgrade-<UTC>/`, собирает wordpress/setup, обновляет плагин, выполняет миграцию и проверяет неизменность старых кодов/URL/UTM/QR/версий/идемпотентности. Затем пересоздаёт только контейнер Nginx для обновления адреса FPM и проверяет `nginx -t`. Не выпускайте новые размещения во время сравнения снимков. Том БД не удаляется. Копии могут содержать конфиденциальные данные: не присылайте их в чат.

После успешного обновления:

```bash
./scripts/integration.sh && python3 tests/http.py
```

Интеграционные тесты расширены для нового носителя, Roistat, смены назначения, реестра и сохранности записей. Локальные проверки: `./scripts/check.sh` — 98 доменных утверждений, 13 проверок доступа API, HTML/JS-контракт и синтаксис. Браузерная проверка нового интерфейса ещё нужна: [docs/ui-acceptance.md](docs/ui-acceptance.md).

## Первый запуск тестового окружения

Нужны Docker Engine с Compose, доступ к реестрам образов, Packagist и GitHub. На машине запуска также нужны `openssl`. Системные службы и пакеты проекта автоматически не меняются.

1. `./scripts/prepare-local.sh` создаст `.env` из примера, тестовый сертификат на 30 дней без запроса пароля Basic Auth. Тестовый сертификат покрывает `utm.cargo.test` и `go.cargo.test`.
2. Откройте `.env` в редакторе, заполните четыре разных пароля БД и WordPress. Пароль WordPress — от 16 символов. Не передавайте секреты в чат и не коммитьте их.
3. **Для нового окружения или проверки lock:** `./scripts/lock-dependencies.sh`. Этот шаг создаёт и проверяет настоящий `plugin/cargo-utm/composer.lock` в контейнере PHP 8.3. Просмотрите и сохраните lock в Git. Не заменяйте установку зависимостей обновлением при каждом запуске.
4. После заполнения `.env` и фиксации lock:

```bash
docker compose up -d --build
```

WordPress автоматически устанавливается, плагин активируется, миграции выполняются, в staging появляются два юнита, общий и два условных знака, шаблоны и онлайн-пресеты. Учётные данные администратора — в `.env`. Сервис `setup` завершается с кодом 0; `go` запускается только после него.

```bash
docker compose ps -a
docker compose logs setup
docker compose exec wordpress wp --allow-root cargo-utm migrate
```

Локальный Nginx слушает **только 127.0.0.1:18080 и 127.0.0.1:18443**. Системный Nginx не используется. Канонические UTM/QR-ссылки имеют HTTPS-порт 443 по заданию. Для работы в браузере добавьте на своём компьютере `utm.cargo.test` и `go.cargo.test` в hosts на 127.0.0.1 и настройте локальный туннель с порта 443 на порт 18443 сервера. Например, SSH forwarding на машине, где разрешён локальный порт 443:

```bash
ssh -N -L 127.0.0.1:443:127.0.0.1:18443 user@server
```

Если стенд запускается на собственном компьютере и 443 свободен, задайте `CARGO_HTTPS_PORT=443`. Порты проверяйте до изменения. Для HTTP-проверок без туннеля используйте `curl --connect-to utm.cargo.test:443:127.0.0.1:18443`. Самоподписанный сертификат подходит только тестам; перед рабочим использованием нужен доверенный TLS.

## Пользователи и интерфейс

В `wp-admin` откройте **UTM и QR**. Администратор создаёт юниты и публикует версии профилей/шаблонов. У сотрудника форма кампании и онлайн- или офлайн-размещения. У просмотрщика — реестр, карточки, расшифровка, CSV.

```bash
docker compose exec wordpress wp --allow-root user set-role USER_LOGIN cargo_editor
docker compose exec wordpress wp --allow-root user set-role OTHER_LOGIN cargo_viewer
```

Это команды для уже созданных индивидуальных пользователей WordPress. По явному запросу пользователя Basic Auth отключён: для доступа к админке, реестру и файлам используется вход WordPress. Старый htpasswd сохранён, но Nginx его больше не использует.

Кампания хранит неизменяемый `utm_id`; код кампании проверяется на уникальность. Онлайн-пресеты редактируются через публикацию новой версии. Для носителей текущая серверная схема полей фиксирована в `Rules.php`; изменение состава обязательных полей требует новой версии кода и правил. Сохранённые размещения сохраняют SVG, UTM, ID шаблона и бренда.

Архив сохраняет редирект, отзыв возвращает 410. При смене назначения администратор обязан указать причину; код, QR и выпущенные UTM сохраняются. Кнопка «Дублировать» открывает форму с новым ключом выпуска.

## Конфигурация

| Значение | Где задавать | Кто меняет |
|---|---|---|
| Среда, внутренний и публичный хост | `.env`: `CARGO_ENV`, `CARGO_UTM_HOST`, `CARGO_GO_HOST` | Оператор |
| Разрешённые лендинги | `CARGO_ALLOWED_HOSTS`, точные ASCII/IDNA-хосты через запятую, без пробелов | Оператор после согласования |
| БД и отдельный пользователь go | `CARGO_DB_*`, `CARGO_GO_DB_*`, `CARGO_TABLE_PREFIX` | Оператор |
| TLS origin | `CARGO_TLS_CERT`, `CARGO_TLS_KEY` | Оператор |
| Юниты, кампании, профили, пресеты | Меню плагина | Назначенные роли |
| Права пользователей | Пользователи WordPress | Администратор |
| Утверждённая векторная геометрия | Справочники → профили → JSON `viewBox`, `paths` | Администратор после утверждения |

Логотипы загружаются как контуры, а не произвольный SVG. Плагин проверяет цвет и контрольную сумму, разрешает только пути; окно логотипа ограничено и не задевает служебные модули. В production выпуск с неутверждённым профилем запрещён. Сохранённый QR повторно не генерируется при скачивании; PNG производится из сохранённого SVG.

## Проверки

```bash
./scripts/check.sh
# После запуска стенда, только staging; создаёт тестовые записи и пользователей:
./scripts/integration.sh
python3 tests/http.py
# На установленном стенде:
docker compose exec nginx nginx -t
docker compose exec wordpress sh -c 'cd /opt/cargo/plugin && composer check-platform-reqs --no-dev && composer audit'
```

Интеграционный тест проверяет миграции, семь типов размещений, повторный выпуск и конфликт формы, дублирование, смену URL, сохранность UTM/QR, аудит и роли. Сохраняет SVG и три PNG на профиль. Контейнер QA проверяет PNG через ZXing-C++, защитные поля и служебные модули; отдельно растеризует SVG через Inkscape и декодирует результат.

HTTP-тест проверяет открытую главную, изоляцию гостевого API, вход WordPress, публичные 404, 302, 410, 405, игнорирование query и GET/HEAD-счётчик. По умолчанию использует тестовые хосты и порт 18443; для других значений передайте переменные окружения. Проверки с существующей WP-сессией, визуальная проверка интерфейса, параллельная нагрузка, отказ БД, Excel/BI и печатный пилот описаны отдельно в отчёте приёмки.

## Главная страница и поисковая индексация

Главная публичного сайта открывает генератор без панели WordPress. Гость готовит UTM, затем входит для сохранения и получения рабочего QR. Реестр и расшифровка доступны после входа с правом cargo_view; просмотрщик попадает в реестр. Черновик формы хранится в sessionStorage до 24 часов и восстанавливается в той же вкладке после входа; создание кампании подтверждается отдельно. Публичный API поддерживает только bootstrap/preview, не читает сохранённые кампании и не пишет в БД. «Hello World» больше не является стартовой страницей, сама запись не удаляется. Для страниц/файлов отдаётся X-Robots-Tag noindex/nofollow/noarchive и WP meta robots. robots.txt допускает чтение этого запрета, а не блокирует роботу доступ к noindex. Окончательное удаление уже известных URL из поиска происходит после обработки поисковой системой. Применение изменений к работающему стенду требует обновления образаwordpress и пересоздания контейнеровwordpress/nginx; данныеБД не сбрасываются.

Рабочий адрес браузера: https://utmqr.kit-rb.com. `utm.cargo.test` — внутреннее имя origin; его не нужно открывать из Windows или подменять им публичный URL. `CARGO_PUBLIC_UTM_URL` задаёт адрес ссылок WordPress.
